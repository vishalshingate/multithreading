# Mastering the OAuth2 & JWT Interview Question

This guide is designed to help you answer the question: **"How is Authentication and Authorization handled in your project?"** or **"Explain the OAuth2/JWT flow."**

---

## 🏗️ 1. The High-Level Architecture (Start Here)

When asked this question, start by describing the architecture.

**Your Answer:**
> "In my current project, we use **OAuth 2.0 with OpenID Connect (OIDC)** for authentication and authorization. We implemented a centralized identity management system using **[Keycloak / Okta / Custom Auth Server]**.
>
> Our architecture consists of:
> 1.  **Client:** The frontend application (React/Angular) or Mobile App.
> 2.  **API Gateway:** The entry point that acts as a **Resource Server** or proxy.
> 3.  **Authorization Server (Identity Provider):** Handles user login and issues tokens.
> 4.  **Microservices:** The backend services that trust the tokens."

---

## 🔄 2. The Authentication Flow (Step-by-Step)

Explain the flow clearly. Don't just say "we get a token". Explain *how*.

**The Narrative:**

### Step 1: Login Request
> "When a user tries to access a protected resource or clicks 'Login', the client redirects them to the **Authorization Server's login page**. We use the **Authorization Code Flow with PKCE** (Proof Key for Code Exchange) because it's the most secure standard for public clients."

### Step 2: Authentication
> "The user enters their credentials (username/password) on the Auth Server. If valid, the Auth Server redirects the user back to our application with an **Authorization Code**."

### Step 3: Token Exchange
> "The client (frontend or BFF - Backend for Frontend) takes this Authorization Code and sends a backend request to the Auth Server to exchange it for:
> *   **ID Token:** Contains user info (OIDC).
> *   **Access Token:** The JWT used for API authorization.
> *   **Refresh Token:** Used to get new access tokens when they expire."

---

## 🔐 3. The API Request Flow (JWT Validation)

Now, explain what happens when the user *uses* the app.

**Your Answer:**
> "Once logged in, every API request from the client includes the **Access Token (JWT)** in the `Authorization` header as a `Bearer` token.
>
> **On the server side (Spring Boot):**
> 1.  **Intercept:** We use `Spring Security` with an `OAuth2ResourceServer` configuration.
> 2.  **Validate signature:** The service validates the JWT signature using the Auth Server's **Public Key** (fetched via JWK Set Endpoint). This ensures the token was issued by us and hasn't been tampered with.
> 3.  **Validate Claims:** We check standard claims:
>     *   `exp` (Expiration): Is the token still valid?
>     *   `iss` (Issuer): Did *our* Auth Server issue this?
> 4.  **Context Setup:** If valid, Spring extracts the `sub` (username) and `roles/authorities` from the token and sets up the `SecurityContext` for the current thread."

---

## 📦 4. Technical Deep Dive: The JWT Structure

If they ask "What's inside the token?", answer this:

> "The JWT is composed of three parts, separated by dots:
>
> 1.  **Header:** Indicates the algorithm used (e.g., `RS256`) and token type (`JWT`).
> 2.  **Payload (Claims):** The actual data.
>     *   **Subject (`sub`):** User ID or Email.
>     *   **Authorities/Roles:** e.g., `ROLE_ADMIN`, `ROLE_USER`.
>     *   **Expiration (`exp`):** Timestamp.
>     *   **Custom Claims:** `tenant_id`, `subscription_level`, etc.
> 3.  **Signature:** The cryptographic proof. It's generated by hashing the Header + Payload with the Auth Server's **Private Key**."

## ❓ 5. Common Follow-Up Questions (Be Ready!)

### Q1: What happens when the Access Token expires?
**Answer:**
"We handle this on the client side using **Refresh Tokens**.
1.  The API returns a `401 Unauthorized`.
2.  The client intercepts this error.
3.  It calls the `/refresh-token` endpoint on the Auth Server using the long-lived **Refresh Token**.
4.  The Auth Server verifies the refresh token and issues a new Access Token.
5.  The client retries the failed request with the new token.
This happens transparently to the user."

### Q2: How do you handle Logout?
**Answer:**
"Logout is tricky with JWTs because they are stateless. We typically:
1.  **Client-side:** Delete the token from local storage/cookies.
2.  **Server-side (Optional but secure):** We can maintain a short-lived **Token Blacklist** (in Redis) for revoked tokens until they naturally expire.
3.  **Auth Server:** Call the upstream logout endpoint to kill the SSO session."

### Q3: Why JWT and not Session/Cookies?
**Answer:**
"We chose JWT for **Scalability**.
*   **Stateless:** The server doesn't need to store session data in RAM or a DB for every user.
*   **Cross-Domain:** JWTs can be easily sent to different microservices or even different domains.
*   **Decoupled:** The resource server (API) doesn't need to check with the Auth Server for every request; it just validates the signature."

### Q4: Symmetric vs Asymmetric Signing?
**Answer:**
"We use **Asymmetric Signing (RS256)**.
*   The Auth Server has the **Private Key** (to sign tokens).
*   All Microservices have the **Public Key** (to verify tokens).
*   This is more secure than Symmetric (HS256) because the microservices don't need to know the secret key."

## 🛠️ Code Snippet (Mental Model)

In Spring Security 5+, the configuration is minimal. You can mention this to show hands-on experience:

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .oauth2ResourceServer(oauth2 -> oauth2
            .jwt(jwt -> jwt.decoder(jwtDecoder()))
        );
    return http.build();
}
```
